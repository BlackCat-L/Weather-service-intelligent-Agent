# 气象服务智能体

面向 **能源 / 交通 / 农业** 的气象服务 Agent。用户用自然语言提问，Agent 自主决定
调用哪些工具——解析地名坐标、拉取气象数据、计算发电出力、检索行业规则——
最后给出**可直接执行**的结论，而不是一堆原始气象数字。

> 目标是回答「**明天下午能不能安排光伏板清洗**」，而不是「明天天气怎么样」。

---

## 与普通天气应用的区别

| | 天气 App | 本项目 |
|---|---|---|
| 交互 | 查数据 | **决策支持**：把气象数据翻译成业务建议 |
| 数据 | 直接呈现数值 | **派生指标**：光伏理论出力、风电功率、作业适宜性 |
| 知识 | 无 | **行业规则库**：灾害分级标准、作业门槛、设备影响 |
| 可信性 | 不涉及 | **数值归因校验**：每个数字都能追溯到工具结果 |

---

## 核心能力

**1. Function Calling 工具编排**
8 个工具，模型自主决定调用顺序与参数。复合问题（查天气 → 算出力 → 检索规则 → 给建议）
由模型自己分解执行，没有硬编码流程。

**2. 混合检索知识库**
BM25（关键词）+ 向量（语义）双路检索，RRF 融合。实测在 3 个典型问题上
**3/3 纠正了纯 BM25 的错误首中**——例如「多少度算高温」，BM25 被"度"字误导命中
「风力等级」，混合检索正确命中「高温标准」。

**3. 多智能体协同编排**
数据 Agent 与知识 Agent 并行检索 → 交叉分析 → 汇总生成。
每个角色有独立的提示词与**工具白名单**（数据 Agent 拿不到知识库工具，反之亦然）。

**4. 数值归因校验（防幻觉）**
回答里的每个数字与日期，都要能在工具返回结果中找到出处，否则标记告警。
归因率作为可观测指标持续追踪。

**5. 完整可观测性**
每次问答产出结构化 trace（工具调用序列、参数、返回值、耗时、归因率），
同时服务四个用途：前端实时展示、问题排查、批量评估、面试演示。

## 快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 配置大模型（复制模板后填入 Key）
cp .env.example .env

# 3. 构建知识库索引
python scripts/build_index.py

# 4. 启动服务
python run.py
```

打开 http://127.0.0.1:8000

| 入口 | 说明 |
|---|---|
| `/` | 对话页（实时轨迹面板 + 出力曲线 + 归因报告） |
| `/kb` | 知识库检索调试台（BM25 / 向量 / RRF 三路对比） |
| `/docs` | FastAPI 自动生成的接口文档 |

命令行体验：

```bash
python ask.py "余杭区明天适合安排光伏板清洗吗？"
python ask.py --multi "..."     # 多智能体模式
python ask.py --tools           # 查看已注册工具
```

前端开发（需要 Node 18+）：

```bash
cd frontend
pnpm install
pnpm dev          # 开发服务器（5173，自动代理 /api 到 8000）
pnpm build        # 构建产物给后端托管
```

## 架构

### 后端分层

```
api/          接口层      只做协议转换（HTTP/SSE → 函数调用）
services/     服务层      业务编排（问答流程、会话管理）—— 唯一业务真相来源
agent/        智能体核心  Function Calling 循环、工具注册表、多智能体编排
kb/           检索层      混合检索（领域无关）
tools/        工具集      气象领域适配 —— 换领域只改这一层
prompts/      提示词      与代码分离，便于单独迭代
infra/        基础设施    LLM 客户端、配置、缓存
checks.py     校验器      数值与日期归因校验
```

**依赖只能单向向下**。`agent/` 和 `kb/` 不认识"气象"这个词——它们与领域解耦，
所以换一个领域（比如金融、医疗）只需重写 `tools/` 和 `prompts/`。

### 前端分层

```
views/        页面        ChatView / KbDebugView
components/   组件        ToolTrace / ChartPanel / VerificationPanel / MarkdownText
stores/       状态        Pinia（对话、SSE 事件处理）
api/          客户端      HTTP + SSE 解析（唯一理解传输协议的地方）
utils/        工具        轻量 Markdown 渲染、工具展示元数据
```

**为什么 SSE 解析要单独抽出来**：组件只消费「事件对象」，不关心事件是 SSE 还是
WebSocket 来的。将来若要支持中途打断生成（需要双向通信），只改 `api/client.ts` 一个文件。

### 为什么用 SSE 而不是 WebSocket

Agent 回答是单向流，提问走普通 POST 就够。SSE 是纯 HTTP、反代友好、浏览器自带重连；
WebSocket 需要 Upgrade 握手且要自己实现重连，在本场景是纯粹的复杂度负担。

## 开发过程中解决的实际问题

> 这一节记录真实踩过的坑与判断过程。**问题是怎样被发现、怎样被定位的**，
> 比"最终代码长什么样"更能说明工程能力。

### 1. 数值归因校验器反过来变成了「工具设计缺陷探测器」

首次跑通时归因率只有 92%，未归因的数字是「下午总发电量 179.4 kWh」——
它是**模型自己把 24 行小时数据加总出来的**，违反了「数值一律由程序算」的原则。

修法不是改提示词，而是给工具**补上 `segments` 字段**（分时段合计/均值/峰值）。
归因率随即升到 100%。

**这揭示了一个反向用途**：未归因的数字往往不是模型在编，而是「工具该给的聚合值
没给，模型只好自己算」。校验器成了工具设计的体检工具。

### 2. 日期幻觉——防幻觉机制不能有旁路

模型在回答里写下「获取时间 2025-06-18」，而当天是 2026-09-19。更棘手的是，
**数值校验没抓住它**——日期被拆成 `2025` / `-06` / `-18` 三个数字，
而 `-6` 和 `-18` 恰好与气象数据里的气温风速撞上了。

根因：主提示词注入了当前日期，但**多智能体编排的四个角色提示词是各写各的、
绕过了这个注入**。汇总 Agent 不知道今天是几号，于是编了一个。

修法：抽出 `with_today()` 公共函数强制所有提示词走它，并新增**独立的日期校验**
（日期幻觉与数值幻觉是两类问题，用一个校验器覆盖不了）。

> 教训：**防幻觉机制如果有旁路，就等于没有。**

### 3. 领域规则建模缺陷——工具答的问题必须和用户问的问题对齐

同一问题，单 Agent 说「不适合清洗（有雷阵雨）」，多 Agent 说「非常适合，全天无风险」。
两个结论矛盾，必有一个错。

根因：风险工具的 `pv` 场景里降水规则是「≥10mm 才算风险」。3.8mm 小雨对设备确实无害，
工具报「无风险」——但**小雨恰恰是不宜清洗的天气**（会形成泥点，且雨量不足以冲刷）。

问题本质：**工具回答的是「有没有设备风险」，用户问的是「适不适合干这件事」，
两者不是一回事，但工具描述里承诺了后者。**

修法：
- 新增 `cleaning` 场景，显式编码作业适宜性规则
- 工具输出增加 `suitable` / `conclusion` 字段直接给结论，
  避免模型把「无设备风险」自由发挥成「适合做任何事」

### 4. Windows 部署白屏——ES module 的 MIME 类型严格校验

本地 Vite 开发一切正常，部署后访问首页**白屏**，控制台报：

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "text/plain"
```

根因：Python 的 `mimetypes` 在 **Windows 上从注册表**读 MIME 映射，而注册表里
`.js` 的 Content Type 常常缺失或被装某些软件时改坏，于是回退成 `text/plain`。
浏览器对 `<script type="module">` 执行**严格 MIME 校验**，类型不对直接拒绝执行。
Linux 上读 `/etc/mime.types`，所以不会有这个问题。

修法：在 `backend/main.py` 里显式注册所需 MIME 类型——**不要依赖操作系统的 MIME 配置**。

### 5. Vue 响应式陷阱——界面一直转圈但后端 200

问答发出后界面永远停在「正在调用工具」，但后端日志显示 `POST /api/chat/stream 200 OK`。
排查方向很容易被带偏到后端。

根因在前端状态管理：创建了**普通对象** `turn` 然后 push 进 `ref` 数组。
Vue 的响应式数组在**读取时**才把元素包成代理，而闭包里持有的始终是原始对象——
后续 `turn.answer = ...` 改的是原始对象，代理的 set 陷阱不会被触发，
**数据确实变了、界面却一动不动**。只有首次 push 触发了渲染。

修法：用 `reactive()` 从一开始就持有代理。

### 6. SPA 深链接 404

前端用 history 模式路由，`/kb` 在服务端没有对应文件，直接访问或刷新会 404。
这是 SPA 部署最常见的坑。修法是加兜底路由：真实文件照常返回，其余路径一律回
`index.html` 交由前端路由解析（`/api` 开头要排除，否则接口 404 会被伪装成 200 的 HTML）。

### 7. 供应商与端点的实测选择

| 供应商 | 延迟 | Function Calling | 结论 |
|---|---|---|---|
| 智谱 `glm-4.5-flash`（免费额度） | 平均 **24.9s** | ✅ 可用 | 免费但被严重限速，不适合演示 |
| 豆包 `doubao-seed-character` | 平均 **0.9s** | ✅ 可用 | 快 27 倍，用于主力 |

另外踩到一个端点坑：智谱的 **coding 端点**（`/api/coding/paas/v4/`）需要单独订阅
Coding Plan，普通 Key 会返回 `429 余额不足或无可用资源包`——**必须用标准端点**。

> 这些结论都来自实测而非文档，且推翻了「免费优先」的初始判断。

## 大模型选型（实测，非看排行榜）

选型的核心矛盾是 **「工具调用稳定性」vs「延迟」**，而不是「谁更聪明」——
我们的任务是判断调哪个工具、填什么参数，属于模式识别而非复杂推理。

用真实工具集跑六项基准（`tests/model_benchmark.py`）：

| 模型 | 通过 | 延迟（默认） | 延迟（关思考） |
|---|---|---|---|
| **`doubao-seed-2-0-mini-260428`** | **6/6** | 3.78s | **0.96s** ← 采用 |
| `doubao-seed-2-0-mini-260215` | 6/6 | 3.49s | — |
| `doubao-seed-2-0-lite-260428` | 6/6 | 18.52s | 3.16s |
| `doubao-seed-character-260628` | 4/6 | 0.86s | — |
| `glm-4.5-flash`（智谱免费额度） | — | 24.9s | — |

### 关键发现：默认的「深度思考」对本项目是纯成本

2.0 系列默认开启思考模式，**延迟增加 4~6 倍**。而我们的任务用不上思考链，
所以关掉它 —— `mini` 档从 3.78s 降到 **0.96s**，比角色扮演模型还快，
同时六项能力全通过。

配置方式（`.env`，无需改代码）：

```bash
DOUBAO_MODEL=doubao-seed-2-0-mini-260428
DOUBAO_EXTRA={"thinking":{"type":"disabled"}}
```

> `*_EXTRA` 是通用的供应商扩展参数机制（JSON 配置），**加新参数不用改 LLM 层代码**。

### 顺带澄清两个常见误解

- **「2.0 比 1.6 更好」这个问法在当前账号上已不成立**：`doubao-seed-1-6-flash`
  返回的是 `does not exist`（而非 `not activated`），说明该版本已下线。
  选型要在**当前可用的**模型里做。
- **角色扮演模型（character）不是不能用**：它 Function Calling 能力够，
  延迟也低，但在「并行工具调用」和「指令遵循」两项上实测**不稳定**
  （同一测试两次结果不同：一次 6/6，一次 4/6）。稳定性对 Agent 比峰值能力更重要。

**三个值得注意的现象：**

1. **知识类题目只调用知识库工具**（`pv-03` / `kb-01` / `kb-02` / `kb-05`），
   没有去查实时天气——说明工具描述的边界足够清楚，模型能分辨「问规则」和「问数据」。
2. **闲聊与非气象问题一次工具都不调**（`edge-02`「你好」、`edge-03`「写快速排序」）——
   这是工具使用克制性的直接验证，也是 Agent 最容易失控的地方。
3. **智谱耗时约为豆包的 10 倍**（66-102s vs 6-11s），印证了供应商选型的判断。

### 评估集抓出的真实问题（最有价值的一条）

首轮全量跑分是 **17/18**，唯一失败的 `fc-02`（「余杭区未来三天适合作户外作业吗？」）
返回的是：

```
（已达到最大工具调用轮次，未能得出最终结论。请把问题拆细一点再问）
```

**根因**：问题问「未来三天」，而 `assess_weather_risk` 一次只能评估一天，
模型必须为每天调一次——三天吃掉三轮工具调用，再叠上地名解析与预报查询，
直接撞到轮次上限而未能给出结论。

**修法不是调大轮次上限**（那只是掩盖问题、且让无效循环更久），
而是让工具支持**日期区间**：

```python
assess_risk(lat, lon, date, scenario, end_date=None)
# end_date 不传 = 单日（保持兼容）；传入 = 区间模式，一次返回逐日结论与适宜日期
```

修复后 `fc-02` 只用 2 个工具、一次区间查询即得出结论（归因率 93%）——
**比修复前还少一次工具调用**。

这个案例说明了评估集的真实价值：它发现的不是一个代码 bug，而是一个
**在真实使用中才会暴露的设计缺陷**——如果只靠手工试几个问题，很难想到
「问多天」这个场景会把轮次吃光。

**同一个模式后来又出现了第二次**：`mix-02`（「杭州最近一周和往年同期比，
气温偏高还是偏低？」）同样耗尽轮次。看轨迹发现它查完最近一周的数据后，
**连着三次去检索知识库**，始终没想到要再查一次去年同期——它想去知识库里
找答案，而答案在历史数据里。

两次的修法是同一个思路：**凡是需要对同一工具用不同参数多次调用才能回答的问题，
就把这个「多步」收进一次工具调用。**

| 问题 | 症状 | 修法 |
|---|---|---|
| `fc-02` 问「未来三天」 | 每天调一次评估工具，三轮耗尽 | 工具支持 `end_date` 日期区间 |
| `mix-02` 问「和往年比」 | 没想到要查去年同期，转去检索知识库 | 工具支持 `compare_yoy`，一次返回两期数据+差值与结论 |

> 这条已经沉淀成设计原则，写在两个工具的 docstring 里。
> 它的价值不限于这两个场景——**只要工具设计允许「一步到位」，
> 模型就不会在「下一步该干什么」上迷路。**

### 问题二：知识库检索触发率只有 40%（RAG 系统的隐形失效）

跑分时发现同一道知识题（「雷暴天气下户外作业要注意什么？」）**时好时坏**：
上一轮调了知识库，下一轮没调。连跑 5 次测量：

```
第1次: （未调用工具）      第4次: （未调用工具）
第2次: [search_weather_knowledge]
第3次: （未调用工具）      第5次: [search_weather_knowledge]
稳定率 2/5
```

**这是 RAG 系统最隐蔽也最致命的问题**：模型有 60% 的概率凭记忆回答。
后果不是「答错」，而是三重损失同时发生：

1. **可追溯性丢失**——回答没有知识库出处，用户无法核对
2. **一致性丢失**——同一问题两次回答的依据不同
3. **知识库价值打四折**——花钱建的知识库只在 40% 的请求里起作用

**根因**：系统提示词只强制了「气象数值必须来自工具」，**没有强制「领域规则必须来自知识库」**。
模型觉得自己知道答案就直接答了。

**修法**（改提示词 + 工具描述 + 降温，三处一起）：

- 系统提示词新增一条铁律：领域规则必须检索，并列举三类必须检索的问题
  （标准阈值 / 行业规定 / 概念原理），明确写出「即使你确信自己知道答案，也必须先检索」
- 工具描述里补上更贴近真实提问的示例（「雷暴天户外作业注意什么」这类常识性问题）
- 温度从 0.3 降到 0.1——事实报告类任务不需要创造性，低温同时减少编造

**修复后：三个知识类问题各跑 5 次，15/15 全部命中，且工具路径完全一致。**

> 教训：**评估一个 RAG 系统不能只看「检索准不准」，还要看「该检索的时候检索了没有」。**
> 前者是检索质量问题，后者是触发率问题——两者的排查方向完全不同，
> 而触发率问题在单次测试里几乎看不出来。

### 问题三：归因率 90.7% 其实是仪表盘坏了，不是模型坏了

切换供应商后归因率从 98.2% 掉到 90.7%，看起来像「新模型更爱编数字」。
但查看未归因的数值清单，它们是 `[-19.0]`、`[-20.0]`、`[2026.0, -9.0, -19.0]`——
**全是日期碎片**。`2026-09-19` 被数字正则拆成 `2026` / `-09` / `-19`，
再被当成「编造的气象数值」扣分。

最极端的例子是 `kb-04`（一道关于预报原理、回答里没有任何气象数值的知识题）
被误判为 **25%**。

**修法**：数值抽取前先剥离日期。但这里有个必须避开的陷阱——
**不能把数值区间一起剥掉**：`22-28°C` 看起来也像「数字-数字」，
如果被误当日期剥离，反而会丢掉真实证据。所以日期识别改用两套严格正则
（ISO 格式需带年份、中文格式需带「月/日」），并加单元测试锁定这个边界：

```
✓ 日期碎片应被剥离            '2026-09-20 … 32.9℃' → ['32.9']
✓ 温度区间不能误剥离          '气温 22-28℃, 风速 12' → ['22','-28','12']
✓ 纯编造数值仍要抓到          '气温 99.9℃, 湿度 88%' → ['99.9','88']
```

修完日期问题后，又发现第二处同类噪声：**有序列表的编号「1.」被当成数值 1.0**。
本想用 `_MIN_ABS=1.0` 阈值挡掉编号噪音，但因为判断是 `>=`，1.0 恰好放行——
一道完全正确的回答因此停在 80%。

这里有个必须避开的取舍：**不能靠抬高阈值解决**，因为「2级风」「3米/秒」
这些是真实数据，抬阈值会把它们一起丢掉。正确做法是**精确剥离列表标记**
（`1.` / `2、` / `3)` / `（4）`），而不是粗暴过滤小数字。

修复后归因率稳定在 **98-100%**。两处噪声都加了单元测试锁定边界：

```
✓ 列表编号应剥离              '1. 撤离时机…'            → []
✓ 温度区间不能误剥离          '气温 22-28℃, 风速 12'     → ['22','-28','12']
✓ 编号与数据混合              '1. 气温 35℃  2. 湿度 88%' → ['35','88']
✓ 纯编造数值仍要抓到          '气温 99.9℃, 湿度 88%'     → ['99.9','88']
```

> 教训：**指标异常时，先怀疑测量工具，再怀疑被测对象。** 这次如果直接去
> 「优化模型的数值纪律」，就是在错误的方向上白费力气——因为模型本来没做错。
> 而且修复要精确：图省事把阈值一调，真实数据也跟着丢了。

## 已知限制

- **地理编码精度**：区县级地名取的是行政区中心点，与具体厂址可能偏差十几公里。
  光伏/风电这类对位置敏感的应用需要精确坐标。
- **光伏/风电模型为简化模型**：未考虑逆变器限幅、遮挡、积灰、尾流、机组可用率，
  结果是理论值。用于趋势判断与排产参考，不能直接当作结算依据。
- **预报时效**：3 天以内的出力预估才有参考价值，更长的时效只能看趋势。
- **评估集规模**：18 题，覆盖主要路径但不足以做统计显著性判断。
